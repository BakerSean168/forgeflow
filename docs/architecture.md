# ForgeFlow Architecture

## Purpose

ForgeFlow owns an engineering objective from durable planning to verified delivery. It separates deterministic control from model-driven reasoning so that intelligence can change *what should happen next* without gaining authority to violate repository, provenance, review, or deployment rules.

## Platform boundary

ForgeFlow is designed as a modular monolith: external systems integrate through the versioned HTTP/OpenAPI boundary, projects enter through a declarative Project Registry, and privileged capabilities enter through narrow typed ports. The controller does not load arbitrary runtime JavaScript plugins because repository/release/provider authority makes plugin code part of the trusted computing base. See [`api.md`](./api.md) and [`extensibility.md`](./extensibility.md).

## Control layers

### Domain and persistence

The durable model records Plans, graph versions, WorkItems, Executions, Reviews, resource selections, ACP runtime-admission cache state, Supervisor direct-admission cache state, worktrees, delivery state, Supervisor state, and immutable events. Terminal state is monotonic and writes use idempotency/CAS where duplicate execution would be unsafe.

### Deterministic kernel

Kernel operations are the only state-changing authority exposed to the Supervisor. Typed actions include creating/continuing/retrying executions, requesting reviews, creating repairs, replanning the remainder, creating bounded child plans, parking external gates, and escalation.

### Orchestration runtime

The runtime advances dependency-ready work through implementation, review, repair, integration, and delivery. It treats each of those as a distinct state rather than collapsing them into “done”. Active-root operator cancellation is also deterministic and fail-closed: the Plan first enters `SAFETY_HOLD`, its Supervisor is retired, every unfinished Execution must become `CANCELLED` (with any live provider session demonstrably quiesced first), unfinished WorkItems are cancelled, and the Plan becomes terminal. When a WorkItem has historical failed attempts plus a live retry, cancellation quiesces active `QUEUED`/`RUNNING` attempts before historical terminal attempts, and orders same-WorkItem history newest-first; an older attempt therefore cannot try to abandon a worktree still owned by its current retry. OpenHands cancellation first requests a graceful pause, then escalates to the supported interrupt operation when the ACP child remains active, and finally deletes the conversation so OpenHands closes the event service and releases ACP runtime resources. ForgeFlow verifies that the conversation is no longer fetchable before accepting remote cleanup, then persists immutable provider-cleanup evidence before touching workspace state. If a recovered OpenHands conversation must be torn down after literal-worktree ACLs were already revoked, cancellation may temporarily restore only that execution's bounded worktree/common-dir access: a live writer must match the cancelling execution, while a quiescent worktree requires the root Plan to already be in `SAFETY_HOLD`; provider teardown still fails closed before any durable cancellation if this access restoration cannot be proven. A historical durable `CANCELLED` Execution that predates this proof is backfilled through the same provider cleanup once; later workspace-cleanup retries reuse the evidence and never re-cancel the provider. If the provider session had already reached an immutable terminal result such as `SUCCEEDED`, `FAILED`, or `STUCK`, cleanup preserves that result as provenance rather than rewriting it to `CANCELLED`; only non-terminal session state is completed as cancelled. A cancelled literal-worktree execution is not considered fully quiesced until its unaccepted repository changes are reset to the execution source revision and its durable writer ownership is released; cleanup failure is retryable without re-cancelling the already-quiesced provider. Terminal provider-session cleanup is a separate release barrier from business-result state. Before any terminal root Plan (`SUCCEEDED`, `FAILED`, or `CANCELLED`) can retire its worktree family or release/handoff the project lease, ForgeFlow traverses the root and every descendant Plan and requires each created provider session to carry durable remote-cleanup proof. Cleanup invokes the immutable selected provider's teardown path, including verified OpenHands conversation deletion, but never rewrites a successful/failed Execution result, accepted SHA, or terminal provider observation and never abandons a successful workspace. Existing cancellation-cleanup evidence is accepted as equivalent proof, making crash/restart replay idempotent. The same cleanup capability is exposed as an explicit terminal-execution operator action for historical recovery. If an older release already retired the literal worktree before provider cleanup, ForgeFlow permits a narrowly fenced compatibility path only when the owning Plan is terminal and the exact persisted worktree record is already `RETIRED`; it then asks the immutable provider to prove deletion/absence without recreating filesystem authority. Any missing retired-worktree provenance, live execution, provider mismatch, or teardown failure remains fail-closed. A provider cleanup that is unavailable, still live, or cannot restore the execution's bounded terminal worktree access blocks retirement and lease release. Worktree retirement must then succeed before the project lease can be released or handed off. A provider that remains live, a held/dirty worktree, descendant Plan, or stale lease therefore blocks handoff instead of being hidden by a terminal Plan label. `FAILED` is a product-result terminal state, not proof that execution resources have been retired: if a FAILED root still owns the project lease, operator cleanup and queue reconciliation run a cleanup-only pass that cancels non-success residual Executions, non-passed Reviews, and unfinished WorkItems, retires the worktree family, and only then releases/hands off the lease while preserving the Plan itself as `FAILED` and preserving each execution's original error provenance. `SUCCEEDED` is never reinterpreted through that cleanup-only cancellation path. Quiescent worktree teardown access is allowed only while the root is in `SAFETY_HOLD`, the root is terminal, or the exact execution's descendant Plan is terminal; otherwise a live writer must exactly match the cancelling execution. Cancellation access proves canonical gitfile/admin/branch/common-dir identity but intentionally does not require the current worktree HEAD to equal the durable accepted revision, because a failed writer may have produced an unaccepted commit; that candidate is never adopted by cleanup, and the later abandon step alone resets the worktree exactly to the execution source revision before writer release. Descendant Plans are cancelled deepest-first through the same operator API: a child enters `SAFETY_HOLD`, retires its own Supervisor, quiesces/cancels its own Executions, cancels non-passed Reviews and unfinished WorkItems, and becomes `CANCELLED`, but it never retires the shared root worktree family or releases the root project lease. Repeating a completed cancellation or FAILED cleanup is idempotent, while repeating one that stopped at execution/workspace cleanup resumes that cleanup before root retirement or lease release.

### Workspace isolation

ForgeFlow supports isolated execution workspaces and shared-common-dir literal Git worktrees. The controller owns workspace topology and provenance; a model receives only the workspace and Git capabilities required for its phase. Independent review is detached at the exact candidate revision and cannot become an implementation writer. Literal worktrees are enabled only for explicit project keys and explicit canonical repositories. Deployment mounts each authorized repository's Git common directory into OpenHands at the identical absolute path; Plan activation independently verifies that the running container has that exact read-write bind mount before any worktree is handed to a model. Every WorkItem/review/repair provisioning and writer-access path replays that root-Plan activation gate, so a durable half-created worktree record cannot bypass project admission after a crash. The integration worktree's durable `baseRevision` is immutable after first activation: when the logical Plan head advances after one accepted candidate, later activation replays must reuse the existing integration worktree's recorded base rather than re-keying the same worktree with the newer `plan.currentRevision`; this preserves idempotency while serial integration continues to advance only `currentRevision`. Concurrent WorkItems single-flight activation before creating their separate worktrees. Before a new parallel wave becomes durable, the controller preflights an executable resource for every selected sibling, then atomically persists their common wave/base, `RUNNING` state, initial execution identities, and immutable resource selections in one SQLite transaction; any admission miss or commit failure leaves every sibling unassigned so a retry preserves the original wave/base instead of silently serializing the Plan. Activation failures are classified before changing Plan state: repository/worktree identity, protected-ref, or other unknown safety failures remain fail-closed in `SAFETY_HOLD`, while an explicit bounded allowlist of infrastructure failures such as Agent Harness admission, OpenHands mount verification, Git I/O, or ACL operations parks the root Plan in `WAITING_FOR_SYSTEM_REPAIR`. Each activation failure records only its normalized error code and disposition in durable Plan evidence. Queue reconciliation retries the lifecycle gate for `WAITING_FOR_SYSTEM_REPAIR`; after the gate succeeds it returns the Plan to `READY` only when no non-terminal repair child exists, and records a durable recovery event before normal automation resumes. `SAFETY_HOLD` Plans keep the project lease fenced and are never automatically reactivated, and terminal Plans are never reactivated during boot. Retirement can safely consume a `PROVISIONING` record whose physical worktree was never created. Controller-created `forgeflow/plans/<project>/<plan>` parents and any intermediate role namespaces such as `items/`, `reviews/`, or `delivery-repairs/` are normalized to controller ownership and mode `0711` after creation, independent of the service umask, so the source Git identity and worker can traverse but cannot list sibling Plan or role state. The worker receives read access to existing loose and packed Git objects, write/default ACLs only on object directories needed to create new objects, and write access only to its Plan-scoped ref/admin namespace. Intermediate common-dir namespaces receive execute-only ACLs; the worker can follow its known worktree/ref/log path without listing sibling state. Worktree-admin and Plan-scoped ref/reflog ACLs preserve both the worker identity and the canonical source owner as access/default entries, so Git's normal atomic replacement of files such as `index` or `refs/heads/forgeflow/.../head` cannot make future controller/source reads disappear. Cancellation and writer re-admission repair source access across those same bounded namespaces before validating linkage, which also lets old worktrees created before the default-ACL rule be retired without weakening branch identity checks. Literal-worktree identity does not trust prompt or environment policy: the worktree root is source-owned and sticky with an explicit worker ACL, while the `.git` gitfile is source-owned and mode `0444`. A model therefore cannot replace or unlink the shared-worktree pointer even after deliberately unsetting ForgeFlow's injected Git configuration. Progress and finalization continuously revalidate that the gitfile resolves strictly inside the canonical `.git/worktrees/*` namespace and that canonical `git worktree list` still reports the expected branch/detached role; linkage drift fails closed as `WORKTREE_GIT_LINKAGE_VIOLATED`. Before accepting an implementation, ForgeFlow also computes the exact `sourceRevision..HEAD` changed-file set and requires every changed path to fall inside the WorkItem's declared `writeScopes` when scopes are present; prompt compliance is therefore not sufficient to cross the review boundary. If a provider finishes immediately after controller-side evidence promotion and recreates `.forgeflow-completion-evidence.json`, integration may remove that late residue only when both the repository copy and the already-durable implementation evidence independently pass the exact execution/SHA gate and decode to the same canonical evidence; a missing, invalid, tracked, or differing replay remains a hard failure before the normal clean-worktree gate. Terminal Plan retirement reuses the same exact-evidence rule before removing a literal worktree, so a verified late completion-evidence replay cannot strand an otherwise clean cancelled Plan, while any unknown or differing dirt still blocks retirement. Cancellation replay is likewise idempotent after a worktree has already been retired only when the durable execution session exactly matches the retired worktree descriptor and the physical path is absent; provenance drift remains fail-closed. A previously corrupted literal worktree is never adopted from its physical Git history: cancellation/retirement may recover only when the canonical worktree registry still identifies the exact managed path and expected Plan branch/detached role. ForgeFlow source-owns and deletes that managed tree without following symlinks, prunes the now-missing canonical admin entry, resets only the Plan-scoped branch to the durable expected revision, and recreates the worktree from the canonical repository before continuing cleanup. Unknown registry/path/lock/role mismatches remain fail-closed. Controller-side read-only Git inspection disables optional index locking so a root control plane cannot accidentally replace a source-owned worktree index. When retry, cancellation, or retirement takes ownership back from a worker, ForgeFlow fail-closed restores the worktree admin metadata to the canonical repository uid/gid and owner access before running source-identity Git cleanup. Plan retirement removes worker ACLs, including shared traverse ACLs, before the project lease may be released. Gitlink submodules are also controller-owned workspace topology: literal worktree creation initializes every exact `160000` gitlink recursively before writer access, verifies the pinned submodule status, and protects each nested `.git` gitfile as source-owned read-only metadata under a sticky submodule root. A failed writer therefore cannot make finalization depend on model-authored repairs to submodule Git metadata. Retry/finalization recovery may rebuild only the exact submodule paths declared by the current superproject HEAD and then re-prove the pinned state; the mutable working-tree `.gitmodules` file is never used as deletion/protection path authority. When a provider committed a clean superproject candidate before local finalization failed, explicit finalization recovery may preserve that exact source-descendant commit only after write-scope and protected-ref proof. It does not synthesize completion evidence: a new real provider execution starts from the preserved candidate, reruns checks, and must still pass independent exact-SHA review.

### Resource selector

Execution resources combine model family, agent backend, transport, resource tier, ordering, health, runtime admission, and durable selection evidence. Selection is deterministic within policy and the chosen resource is immutable for an Execution. ACP runtime admission is demand-driven: an idle control plane does not periodically launch probe conversations, while READY/RUNNING/WAITING_FOR_RESOURCE Plans or active Executions trigger admission before automation or an explicit run/reconcile action proceeds. Admission outcomes are durably cached with bounded success/failure TTLs, so a control-plane restart can reuse a still-fresh sanitized readiness result instead of immediately launching another ACP probe. Runtime-admission identity is phase-scoped: IMPLEMENT and REVIEW probes cannot silently alias merely because they share a `codex-acp` backend, and health `implementationReady` / `reviewReady` counts are derived from that explicit phase identity rather than backend-name heuristics. Autonomous polling advances existing Executions before it refreshes runtime admission; admission refresh runs as its own single-flight, so a slow or unhealthy standby route cannot starve active execution heartbeat, inspection, or stall recovery. A Plan that needs a not-yet-admitted new resource waits fail-closed until a later poll sees the refreshed admission result. Each actual probe has a stable recovery-group identity and a unique attempt identity/workspace. The stable group lets a later attempt recover and delete an OpenHands conversation even when the previous process died after server-side creation but before receiving the conversation id; the unique attempt prevents a restarted control plane from deleting a workspace still in use by an older process. Planned SIGTERM/SIGINT shutdown aborts the probe request path, stops new admission cycles, and then completes non-cancellable inspect/interrupt/delete compensation before the database closes. Once remote group cleanup has completed, stale attempt workspaces (including the older deterministic layout) are pruned fail-closed without following symlinks. DSH ACP launch execs the actual DSH process rather than the signal-dropping wrapper, so OpenHands owns the process it must terminate instead of leaving a grandchild adopted by the container init. The cache stores only route identity, readiness, sanitized error code, and check time; readiness/error transitions are audited, while TTL refreshes do not generate event spam. A disabled runtime exposes the durable cache read-only but does not hydrate those rows as active readiness. Operator resource or binding state changes invalidate the matching durable and in-memory ACP admission entries before any subsequent selection, and directory reconciliation drops admission rows for routes that no longer exist; reactivation therefore cannot reuse a pre-change `ready=true` result merely because its TTL has not expired. Meaningful-progress recovery is tier-aware: FREE/PROMOTIONAL implementation and implementation-fix executions use a shorter opportunistic stall budget and reset that budget only when the durable workspace fingerprint changes. Repeated reads, changing provider event ids, pending/completed tool-call pairs, or failed edits therefore cannot keep a free coding route alive forever when it produces no repository progress. Opportunistic routes also default to zero same-resource session replacements after the bounded window. REVIEW remains provider-progress-aware because an independent reviewer is intentionally read-only, while SUBSCRIPTION/METERED execution keeps the standard longer timeout and provider-or-workspace progress semantics. Global limits always act as upper bounds. Implementation no-op and meaningful-progress stall are execution-route quality failures: they remain retryable and exclude the prior route through immutable execution lineage, but they never suspend the shared resource or sibling bindings. Only provider/infrastructure lifecycle failures such as transport, authentication, quota, provider service, model, or route failures feed ResourceState. Transient resource suspension is recovery-gated rather than timer-only: community/free resources probe after their longer suspension and disable on a failed recovery probe, while metered/subscription resources probe after each bounded cooldown and remain suspended for another cooldown when the probe still fails. LiteLLM probes honor each binding's declared wire protocol (`/chat/completions` or `/responses`) and never persist provider response bodies. Resource-level recovery requires every remaining enabled/ready managed binding to pass; a separately disabled binding is excluded from that recovery quorum. Automatic `SUSPENDED -> ACTIVE` recovery only clears ForgeFlow's resource-level routing fence; it never removes an independently managed binding-level block. Only an explicit operator resource activation carries the broader remote-unblock semantics.

### Production autonomous lifecycle acceptance

The operator-only `npm run smoke:autonomous-lifecycle` command is the repeatable real-provider acceptance gate for the autonomous engineering loop. Its default hard deadline is 45 minutes (operator-bounded up to 90 minutes), deliberately larger than a single standard execution window so admission recovery plus one infrastructure-failed review and its healthy replacement cannot create a false-negative whole-run timeout. It is intentionally excluded from ordinary unit/CI execution because it creates a real Plan and spends provider resources. The runner derives its base from the project's durable lease `committedRevision`, creates two unique non-overlapping `parallelSafe` WorkItems through the public control-plane API, and waits for the same autonomous polling used in production. It fails unless both WorkItems share one wave/base, real implementation executions and workspaces are independent, each accepted SHA has an independent exact-SHA PASS review, the final logical head contains both candidate histories, every provider session has durable cleanup proof; OpenHands-backed sessions have no surviving conversation, while provider-native Antigravity sessions have an inactive/failed execution unit and no matching host process; every Plan worktree is `RETIRED`, the project lease is released at the final logical head, Plan-scoped refs are gone, no provider process remains tied to the Plan, no `PLAN_ACTIVATION_FAILED` event occurred, and the canonical checkout is byte-for-byte untouched and clean. `SAFETY_HOLD` is an immediate smoke failure and includes the durable activation-event evidence in the result instead of waiting for the overall timeout. On timeout or failure it uses only the public Plan cancellation path for best-effort resource retirement; it never edits the control-plane database. The runner also binds the proof to the `HEALTHY` release provenance observed before Plan creation. After all external Git/OpenHands/process checks pass, it POSTs an attestation request to the control plane. The control plane independently revalidates durable Plan truth, exact-SHA review lineage, provider cleanup evidence, worktree retirement, lease/head state, parallel start timing, and absence of activation failures before appending an immutable `MAINTENANCE` event keyed by the release source SHA. `/api/health` exposes this as `autonomousLifecycleAcceptance`: a newly released artifact is `MISSING` until that exact source SHA + artifact digest has passed the real-provider lifecycle, and a release change during the smoke causes the attestation to fail rather than inheriting an older proof.

### AI Supervisor

The Supervisor consumes a bounded projection of durable state and returns exactly one typed decision. It can diagnose unusual failures or alter the remaining plan, but it cannot execute arbitrary shell commands, mutate the database, fabricate evidence, approve its own implementation, or bypass safety gates.

Supervisor reasoning is itself governed by the Resource Selector. There is no production static model alias or alternate Supervisor endpoint: each decision selects a `REASONING` resource through the `SUPERVISE` phase, records sanitized selection provenance, and uses a bounded failover budget. Readiness is path-specific: implementation/review candidates retain ACP runtime admission, while Supervisor candidates pass an independent direct-protocol admission that exercises the same Chat/Responses endpoint, system prompt, JSON-output contract, and typed-decision parser used by the real Supervisor. A generic provider health probe is therefore insufficient to admit reasoning traffic. Direct-admission results are durably cached with bounded success/failure TTLs, so a control-plane restart does not immediately repeat a paid probe. Admission probing is demand-driven: when no non-terminal Supervisor exists, ForgeFlow preserves the cache but does not spend periodic provider requests merely to keep it warm. The cache stores only route identity, readiness, sanitized error code, and checked time; readiness/error transitions also leave immutable audit events. The control-plane exposes this durable cache read-only even while the Supervisor runtime is disabled, but cached rows are never counted as active readiness unless the runtime hydrates them under the normal admission policy. Reading the cache never triggers a provider probe. It never stores provider response bodies or credentials, and it does not poison a resource that may remain healthy for implementation. Provider/network/quota failures from a real Supervisor turn still feed the normal resource-health policy before trying the next eligible reasoning resource. A malformed decision is rejected without globally poisoning an otherwise healthy provider. Its sanitized failure stage/code is recorded against a semantic decision-context digest that excludes Supervisor housekeeping, and that resource is durably excluded while the actionable context remains unchanged.

If all eligible reasoning candidates are exhausted, the Supervisor parks in `WAITING_FOR_RESOURCE` instead of repeatedly spending requests. Recovery is event-driven: when a resource becomes eligible for the same `SUPERVISE` selector policy, ForgeFlow appends a sanitized resource-availability event and schedules a durable `RESOURCE_TRANSITION` wake for waiting Supervisors. Startup reconciles the same condition so provider recovery during downtime is not lost. A 15-minute `RESOURCE_WATCHDOG` remains as a fail-safe recheck and is explicitly allowed to re-evaluate an unchanged observation cursor; normal stale wakes remain rejected. Implementation-only resource recovery does not wake a reasoning Supervisor. Both Chat Completions and Responses protocol bindings are honored according to the selected resource contract.

## Delivery invariant

An implementation commit is not equivalent to accepted work. The normal acceptance chain is:

```text
implementation commit
  -> independent exact-SHA review
  -> accepted/integrated Plan revision
  -> required CI
  -> exact-head PR/merge verification
  -> delivery complete
```

A failure at a later stage preserves the earlier evidence and produces a repair/recovery path rather than rewriting history.

Release promotion carries its own fail-closed provenance. The release builder hashes the exact detached-SHA artifact and, when the Antigravity systemd execution plane is installed, synchronizes its root-owned unit runner, mount sandbox, and unit file from that same detached SHA and byte-verifies the installed helpers before any release provenance is written. The Antigravity unit accepts either the compatibility execution workspace or the current literal Plan-worktree layout, but binds literal review paths to the exact execution id and implementation/repair paths to the exact WorkItem id plus project/Plan/phase request provenance. The builder then atomically installs the control-plane artifact and writes a root-owned `PENDING` record containing the source SHA and artifact digest before restarting the service. The control plane binds that identity at process boot: a pre-existing process therefore reports `MISMATCH` if the on-disk candidate identity changes underneath it. Only the restarted process may expose the matching `PENDING` identity, after which the release gate promotes the same record to `HEALTHY` and verifies it again. Missing, malformed, symlinked, or identity-drifted provenance never becomes release evidence. This exact live identity is a prerequisite for any future ForgeFlow self-change promotion gate.

## Improvement loop and self-change boundary

ForgeFlow can deterministically aggregate repeated bounded execution failures into durable Improvement Candidates. Discovery is read-only with respect to project repositories: it is scoped to the Maintenance program's project/repository, normalizes free-form error tails into bounded stable failure labels before grouping, deduplicates by project/repository/phase/failure identity, and records only the sanitized label as Candidate title/evidence before any model is consulted. Candidate discovery and Plan adoption remain separate gates.

An optional **Improvement Diagnostician** adds cross-Plan reflection without becoming another control plane. It runs only after deterministic Candidate creation and only for explicitly allowlisted Improvement projects. Its model input is a controller-generated `contextRef`, the current risk, a sanitized failure phase/code/count, and up to twelve recent matching observations carrying only opaque `ev-<hash>` evidence refs plus sanitized route/status/timestamp metadata. Real Candidate, Program, Plan, and Execution identifiers are not sent to the model. Raw logs, provider response bodies, prompts, result summaries, credentials, repository contents, and free-form provider error text are deliberately excluded. The selected model must use the normal governed `REASONING` resource policy through the dedicated `DIAGNOSE` phase; provider-native routes and static model aliases are not accepted. The same demand-driven direct Chat/Responses admission used for governed reasoning validates transport readiness before a diagnostic request is spent, and no admission probe is kept warm merely because a previously diagnosed `NO_ACTION` Candidate remains pending.

The model can return only a versioned typed `PROPOSE_REPAIR` or `NO_ACTION` object containing the exact controller `contextRef`, a fixed classification/confidence/risk vocabulary, bounded diagnosis/objective text, 2–8 independently verifiable acceptance criteria for repairs, and opaque evidence refs that must be a subset of the controller-supplied observations. Extra fields, ungrounded refs, credential requests, direct repository/deployment authority, or proposals to disable/bypass/weaken tests, review, approvals, policy, or safety gates are rejected. Malformed diagnosis output excludes that reasoning route only for the unchanged diagnosis-context digest and tries the next eligible resource; it does not globally poison a provider that may be healthy. Provider/network/quota failures still feed normal resource lifecycle state. Every accepted diagnosis is immutable audit evidence with exact resource/binding/model/route/protocol provenance. A diagnosis may raise Candidate risk but can never lower it.

When AI diagnosis is disabled, existing Improvement behavior is unchanged. When enabled, deterministic discovery is prevented from auto-adopting before diagnosis. `NO_ACTION` remains non-adopting. A `PROPOSE_REPAIR` may flow into automatic adoption only when the program is `STANDARD`, adoption and global low-risk auto-adoption are enabled, and the Candidate is still durably `LOW` risk after diagnosis. `CONSERVATIVE` programs always require explicit adoption; medium/high risk work is never auto-adopted, and high-risk explicit adoption still requires acknowledgement. Programs are durably ACTIVE/DISABLED and can be stopped without deleting audit history.

Adopting a Candidate does not grant Maintenance or the Diagnostician a writer. It creates an ordinary root Plan with a normal WorkItem, project scheduling lease, Supervisor, Resource Selector policy, implementation execution, independent exact-revision review, integration, and delivery requirements. A safe `PROPOSE_REPAIR` may enrich that WorkItem with its bounded objective and acceptance criteria, but deterministic root-cause, regression, existing-verification, and independent exact-revision review criteria are always appended and cannot be removed by model output. For non-self work, Candidate completion is derived from that linked Plan: `SUCCEEDED` closes the Candidate, while cancellation makes it stale. Self-change deliberately adds the stronger canary/promotion proof described below, so Plan success alone never closes a ForgeFlow self Candidate. No Candidate can mark itself complete or fabricate review/delivery evidence. A bounded periodic cycle may discover, diagnose, safely auto-adopt eligible low-risk work, reconcile linked terminal Plans, and—only behind the separate self-promotion gates—request an externally executed release; it never receives an in-process privileged repository writer.

Self-change has three independent hard gates. Even if the `forgeflow` project is accidentally included in the Improvement project allowlist, a Plan targeting ForgeFlow's own repository is rejected unless `FORGEFLOW_IMPROVEMENT_SELF_CHANGE_ENABLED=true`. A self-change Plan reaching `SUCCEEDED` still leaves its Candidate `ADOPTED`: it must first pass an exact detached-SHA canary that performs the production build, boundary check, typecheck, complete test suite, artifact smoke boot, and deterministic artifact digest. `FORGEFLOW_IMPROVEMENT_SELF_PROMOTION_ENABLED=true` is then required before ForgeFlow may durably request a live release, and `FORGEFLOW_IMPROVEMENT_SELF_AUTO_PROMOTION_ENABLED=true` is separately required before the periodic Improvement loop may run that canary and request promotion without an explicit API call.

Live promotion deliberately crosses a process boundary. The control plane writes only a bounded root-owned promotion request containing Candidate/Plan identity, exact source SHA, exact canary artifact digest, and canary attestation id. A systemd path unit starts a separate oneshot promotion runner, so restarting `forgeflow.service` cannot kill the process performing its own release. The runner never loads `forgeflow.env` or provider credentials; immediately before release it requires the live `/api/health` projection to report `selfPromotionEnabled=true`, so disabling the gate also invalidates stale request files. The release builder accepts the exact source SHA without advancing `refs/forgeflow/release-approved`, rebuilds in an exact detached worktree using the same build shape as the canary, rejects any artifact digest mismatch before swapping files, backs up durable state, atomically installs the artifact, and verifies `PENDING` then `HEALTHY` boot-bound provenance. Only after that verification may it atomically fast-forward the approval ref. On the new boot, the Improvement runtime compares the durable promotion request with live `HEALTHY` source SHA and artifact digest; only that reverse proof records `IMPROVEMENT_SELF_PROMOTED` and moves the Candidate to `COMPLETED`.

The checked-in deployment defaults discovery, AI diagnosis, adoption, low-risk auto-adoption, project allowlists, self-change, self-promotion, and autonomous self-promotion to disabled. Enabling AI diagnosis additionally requires execution runtime, the governed Resource Selector, and a non-empty Improvement project allowlist; there is no diagnosis-specific static model setting. Production promotion request paths are fixed to `/var/lib/forgeflow/self-promotion-request.json` so the control plane and systemd watcher cannot silently diverge. These defaults preserve the operating mode in which ForgeFlow may observe or represent improvement work without silently rewriting its live code, prompts, policy, or release state.
